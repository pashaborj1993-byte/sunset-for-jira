# GitHub client ready

Optimize for a buyer who decides in five minutes whether to request a conversation.

## Assess the public signal

Check the profile and pinned repositories for a clear service or product category, a working demo path, tests or verification, data and security boundaries, and a contact route. Flag unfinished repositories that weaken the signal; archive them only with owner approval.

## Improve the repository

Place the buyer outcome at the top of the README, followed by a demo, concrete capabilities, architecture or trust boundaries, setup, and known limitations. Prefer a short public demo over a long feature inventory. Link to a pilot or evaluation path where one exists.

Do not publish secrets, private customer names, production credentials, personal contact information, or invented outcomes. Do not claim compliance, availability, or revenue without evidence.

## Keep it maintained

For each public project, establish a small release routine: issue triage, reproducible checks, dependency update cadence, release notes when behavior changes, and a working support route. Update the portfolio only after verifying external links and visible claims.

## Deliver

Return the three strongest proof points, the three conversion blockers, and a prioritized list of changes. If a public change represents the owner or solicits customers, obtain their approval before publishing it.
